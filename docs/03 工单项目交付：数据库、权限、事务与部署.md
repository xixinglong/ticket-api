# 03 工单项目交付：数据库、权限、事务与部署

> [!info] 2026-10-31 补充入口
> 面向初学者的逐模块课件见 [[03-00-小白上手路线与操作地图]]；明日验收见 [[03-交接记录与明日检查清单]]。当前项目实际根目录为 C:\xixl-study\java-labs\ticket-api，后文通用示例路径需按此调整。按最新安排先完成后端和课件，前端暂缓，原最终目标保留用于后续验收。

接口能返回 JSON，只是第一步。接下来要回答三个问题：服务重启后数据还在吗，别人能不能改我的工单，更新到一半失败怎么办？

**这篇是项目实施与验收清单，包含关键 SQL 和设计示例，不是一份复制后就完整运行的后端工程。** 建议按“持久化 → 事务 → 登录权限 → 并发 → 部署”的顺序完成，每次只验证一个新增能力。

## 一、先把业务边界定死

本项目只有两种角色：普通用户 USER 和处理人 AGENT。

用户创建工单、查询自己的工单、取消自己的待处理工单。处理人查询待接单工单、接单、查询并解决自己负责的工单。

工单只允许以下变化：

```text
OPEN → IN_PROGRESS → RESOLVED
OPEN → CANCELLED
```

第一版不支持重新打开、转派、批量操作和管理员任意改状态，减少不必要的分支。

具体规则如下：

- 创建：创建人由登录身份确定，初始状态固定为 OPEN。
- 接单：操作者必须是 AGENT，工单必须为 OPEN，尚无处理人。
- 解决：操作者必须是该工单的处理人，状态必须为 IN_PROGRESS。
- 取消：操作者必须是创建人，状态必须为 OPEN。

不要允许客户端直接提交最终状态，再由后端照单全收。服务端根据具体动作决定状态变化。

## 二、先学会写 SQL，再接 MyBatis

第三周先在独立练习数据库里做四件事：插入、按编号查询、带条件分页、带条件更新。

下面的建表语句只用于新建的练习数据库，不要直接在公司库执行。连接、建库和数据库账号需要你先准备好。使用 MySQL 的 InnoDB 表，本例按 MySQL 8.4 语法编写。

### 工单表只保留必要字段

```sql
CREATE TABLE tickets (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    title VARCHAR(100) NOT NULL,
    creator_id BIGINT NOT NULL,
    assignee_id BIGINT NULL,
    status VARCHAR(20) NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    INDEX idx_creator_id (creator_id, id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

编号和创建人不能为空。处理人允许为空，因为 OPEN 工单还没有被接走。

本节没有给出用户表，也没有建立用户外键。接入登录模块后，需要建立用户主键和数据关联约束；不能把缺失的用户模块当成已经实现。

### 操作记录单独存

```sql
CREATE TABLE ticket_events (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    ticket_id BIGINT NOT NULL,
    actor_id BIGINT NOT NULL,
    action VARCHAR(30) NOT NULL,
    created_at DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
    INDEX idx_event_ticket (ticket_id, id),
    CONSTRAINT fk_event_ticket
        FOREIGN KEY (ticket_id) REFERENCES tickets(id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

这张表回答“谁在什么时候做了什么”，不要用一段控制台日志代替业务记录。

### 先做一次能看到结果的 SQL 练习

在刚建好的练习库里，使用下面的虚构数据。这里的 `1001` 只是假设的创建人编号，不能当作已经接入登录。

```sql
INSERT INTO tickets (title, creator_id, status)
VALUES ('登录页面空白', 1001, 'OPEN');

SET @ticket_id = LAST_INSERT_ID();

SELECT id, title, status
FROM tickets
WHERE id = @ticket_id;

UPDATE tickets
SET status = 'CANCELLED'
WHERE id = @ticket_id
  AND creator_id = 1001
  AND status = 'OPEN';

SELECT ROW_COUNT() AS changed_rows;
```

保持同一个数据库连接执行。第一次更新后 `changed_rows` 应为 1；紧接着只重复执行 UPDATE 和 `SELECT ROW_COUNT()`，结果应为 0。不要在 UPDATE 和读取行数之间插入其他 SQL。

这是理解条件更新的独立练习，没有写操作记录，也没有登录检查，不能拿来代替完整的取消接口。

### 查询自己的工单

下面的 `?` 表示预编译参数，不能原样粘到普通 SQL 控制台里直接执行。依次绑定创建人编号、每页数量、偏移量：

```sql
SELECT id, title, status, created_at
FROM tickets
WHERE creator_id = ?
ORDER BY id DESC
LIMIT ? OFFSET ?;
```

服务端把每页数量限制在 1–100；偏移量由页码计算，拒绝负值并避免整数溢出。不要接受任意列名作为排序参数，第一版固定按编号排序。

这里的索引是配合“按创建人筛选”的候选设计。用代表性数据和 `EXPLAIN` 验证，不凭一张空表就宣称查询已优化，也不要为了覆盖所有字段创建超宽索引。

SQL 语法与 InnoDB 行为参考：[MySQL 8.4 官方手册](https://dev.mysql.com/doc/refman/8.4/en/)。

## 三、接入数据库时只换一层

保留 Controller 的接口约定，逐步把 Service 的内存 Map 替换为 Mapper 调用。不要同时重做接口、前端和数据库结构，出了错会很难定位。

按这个顺序接入：

1. 根据 Spring Boot 主版本选择兼容的 MyBatis Starter，再添加 MySQL JDBC 驱动。
2. 配置数据库地址、用户名和密码；密码从环境变量读取，不写入仓库。
3. 新建表示数据库行的对象，明确下划线列名如何映射到 Java 字段。
4. 为创建、查询分别写 Mapper 方法。
5. 用同一组 HTTP 请求验证接口行为。
6. 重启应用，再查之前创建的工单。

最小连接配置放在 `C:\java-labs\ticket-api\src\main\resources\application.properties`，保留此前的本机监听配置：

```properties
spring.datasource.url=${DB_URL}
spring.datasource.username=${DB_USER}
spring.datasource.password=${DB_PASSWORD}
```

`DB_URL` 的结构示例是 `jdbc:mysql://127.0.0.1:3306/ticket_lab`；使用前先创建对应数据库，并在启动进程的环境中提供这三个变量。密码用专门的本地配置方式输入，不写进仓库、截图、日志或分享出去的命令。IDE 与终端的启动环境分别检查。

在 Mapper 扫描、XML 位置和数据对象还没有配好前，不把“应用能启动”当成“数据库接入完成”。不要通过开启自动删表重建来掩盖表结构不一致。

参考：[MyBatis Starter 兼容说明](https://mybatis.org/spring-boot-starter/mybatis-spring-boot-autoconfigure/)。

一个 Mapper XML 的查询片段可以写成：

```xml
<select id="findById" resultType="com.example.ticket.TicketRow">
  SELECT id, title,
         creator_id AS creatorId,
         assignee_id AS assigneeId,
         status
  FROM tickets
  WHERE id = #{id}
</select>
```

此片段不是完整文件。使用前需定义 `TicketRow`、对应 Mapper 接口和 XML namespace，并配置 Mapper 扫描与 XML 位置。接口参数可显式标注 `@Param("id")`，避免依赖编译参数名推断。

`#{id}` 用于绑定数据参数。不要把用户输入通过 `${...}` 拼进 SQL；如果以后支持动态排序，应由服务端白名单映射列名。

参考：[MyBatis SQL 映射与参数](https://mybatis.org/mybatis-3/sqlmap-xml.html)。

## 四、事务从一次失败开始学

取消工单需要做两次写入：

1. 把工单状态从 OPEN 改为 CANCELLED。
2. 插入一条取消记录。

如果第二步失败，第一步也应撤销，否则就会出现“工单已取消，却没有操作记录”。

事务应围绕完整业务动作，而不是给每条 SQL 各套一个互不关联的事务。

下面是 Service 结构示意，省略了领域异常和 Mapper 的具体定义，不是可单独编译的文件：

```java
@Transactional
public void cancel(long ticketId, long actorId) {
    int changed = mapper.cancelOpenTicket(ticketId, actorId);
    if (changed != 1) {
        throw new TicketConflictException();
    }
    eventMapper.insert(ticketId, actorId, "CANCEL");
}
```

本例约定 `TicketConflictException` 继承 `RuntimeException`。两个 Mapper 必须参与同一个数据库事务，通常使用同一数据源及正确配置的事务管理器。

测试时，主动让事件插入抛异常，然后在事务结束后重新查询数据库，确认工单仍为 OPEN。不能只看到方法抛异常，就推断数据已经回滚。

Spring 默认代理模式下，事务调用需要经过代理；同类内部直接调用带 `@Transactional` 的方法，并不因此自动开启新事务。默认回滚规则也不是“所有异常都回滚”：运行时异常与 Error 默认触发回滚，受检异常需要相应配置。不要在方法里吞掉异常后继续返回成功。

参考：[Spring 声明式事务与注解规则](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)。

## 五、权限判断不要只放在按钮上

前端隐藏取消按钮，只影响用户界面。别人仍然可能直接构造 HTTP 请求，所以服务端每次操作都要重新检查。

把两个问题分开：

- **身份认证：** 这个请求代表谁？
- **操作授权：** 这个人能不能操作这张工单？

登录实现优先使用 Spring Security 已有机制。不要自制明文密码表，不把 MD5 或普通 SHA 摘要当作密码存储方案，也不要自行设计 token 签名算法。

本项目可先选同源页面配合服务端 Session。创建、取消等写请求保留 CSRF 防护，前端按所选安全配置发送 CSRF token；不要为了让请求通过就全局关闭防护。生产 HTTPS 环境再正确配置会话 Cookie 的安全属性。

参考：[Spring Security 密码存储](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)、[Servlet CSRF 防护](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html)。

### 查询接口也要检查权限

不能只保护“取消”，却允许用户遍历所有编号读取他人工单。

本项目约定：普通用户只能看到自己的工单；处理人可看到 OPEN 工单以及分配给自己的工单。不可见对象统一按 404 处理，避免通过详情接口泄露资源存在性。

这个约定需要落实到列表条件和详情查询，不能只在前端过滤。

## 六、并发接单靠数据库条件守住

下面这段思路存在竞争窗口：

```text
先查工单是 OPEN
→ 判断可以接单
→ 把状态更新为 IN_PROGRESS
```

两个请求可能都在更新前读到 OPEN。不要以为给 Java 方法加了事务，就自动解决了这个问题。

把条件放进同一条更新语句：

```sql
UPDATE tickets
SET status = 'IN_PROGRESS', assignee_id = ?
WHERE id = ?
  AND status = 'OPEN'
  AND assignee_id IS NULL;
```

本项目没有重新打开工单的状态路径。在 InnoDB 上，这个条件更新配合受影响行数，可以用于竞争同一张 OPEN 工单：只有更新成功的请求才记录接单成功；未更新任何行的请求不能仍然返回成功。

Service 先验证处理人身份，再执行更新，并检查返回值是否为 1。接单记录仍然要和状态更新处于同一事务。

取消也采用相同思路：

```sql
UPDATE tickets
SET status = 'CANCELLED'
WHERE id = ?
  AND creator_id = ?
  AND status = 'OPEN';
```

0 行表示“不满足更新条件”，不能仅凭这个结果断言一定是“工单不存在”。对于已确认可见的对象可以返回 409；不可见或不存在的对象按项目约定返回 404。前置检查之后状态仍可能变化，所以最终的条件更新不可省略。

这是本项目的实现选择；需要用真实 MySQL 并发测试验证，不能用单线程内存测试代替数据库证据。背景参考：[InnoDB 锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)。

## 七、接口范围控制在这几个动作

- `POST /api/tickets`：创建，成功返回 201。
- `GET /api/tickets`：按可见范围分页查询，成功返回 200。
- `GET /api/tickets/{id}`：详情，成功返回 200。
- `POST /api/tickets/{id}/claim`：接单，成功返回 204。
- `POST /api/tickets/{id}/resolve`：解决，成功返回 204。
- `POST /api/tickets/{id}/cancel`：取消，成功返回 204。

项目约定：未认证返回 401；角色无权执行该类动作返回 403；不可见对象返回 404；可见对象的状态冲突返回 409。REST 接口的未认证处理应配置为 JSON/状态码响应，不默认依赖网页登录跳转。

统一错误响应可以包含稳定的 `code`、可读的 `message` 和用于查日志的 `requestId`。不要把 SQL、数据库口令、完整堆栈或会话凭据返回给前端。

这些是本项目的接口契约，前后端与测试必须使用同一份约定。

## 八、先写这些测试，再考虑增加功能

### 单元测试：验证纯业务规则

标题为空被拒绝；创建人可以取消 OPEN 工单；其他人不能取消；已接单工单不能取消。

### 接口测试：验证输入输出

创建返回 201；非法输入返回 400；未登录返回 401；不可见详情返回 404。还要测试异常是否转换成统一错误结构。

### 数据库集成测试：验证真正的数据行为

- 服务重启后，数据仍能查到。
- 状态更新后事件写入失败，整体回滚。
- 两个独立事务同时接单，只有一个成功。
- 失败请求不会多插入一条成功事件。
- 分页排序稳定，第一页与第二页不因缺少排序而随意变化。

并发用两个请求或两个线程，通过同步屏障尽量同时发起；分别使用真实事务，并检查最终处理人、状态和事件数量。不要求固定是哪一个人抢到。

不要把“写了测试文件”记作“测试通过”。保留实际执行结果与环境版本。
