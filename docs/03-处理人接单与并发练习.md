## 1. 先理解这次增加的内容

| 账号 | 编号 | 角色 | 本阶段允许的操作 |
| --- | --- | --- | --- |
| alice | 1001 | USER | 创建、查看自己的工单、取消自己的 OPEN 工单 |
| bob | 1002 | USER | 同上，与 alice 的数据隔离 |
| agent1 | 2001 | AGENT | 查看未分配的 OPEN 工单、接单、查看自己接下的工单 |
| agent2 | 2002 | AGENT | 同上，与 agent1 竞争接单 |

这些是内存练习账号，尚未接入用户表。处理人不能创建或取消工单。创建人仍能查看被接下的工单，但此时不能再取消。

接单接口为 POST /api/tickets/{id}/claim，无需 JSON 请求体。处理人编号来自登录会话，不能通过 assigneeId 或 actorId 参数指定。成功返回 204。原有详情响应格式保持不变，处理人编号通过 DBeaver 查看。

表中已有 assignee_id，本阶段不需要执行建表或改表 SQL，也不要修改或删除工单 34。

## 3. 在启动服务的 PowerShell 窗口设置两个处理人密码

若旧服务正在运行，先在它的窗口按 Ctrl+C，避免再次占用 8080。继续使用保留 DB_*、LAB_ALICE_PASSWORD、LAB_BOB_PASSWORD 的窗口，增加以下两个变量：

## 4. 在第二个 PowerShell 窗口验证接口

~~~powershell
Set-Location 'C:\xixl-study\java-labs\ticket-api'
.\scripts\Test-TicketClaim.ps1
~~~

脚本提示输入 alice、agent1、agent2 的登录密码，然后创建一张新工单，顺序验证：

| 操作 | 预期状态码 |
| --- | --- |
| 未登录接单 | 401 |
| alice 尝试接单 | 403 |
| 接单前 agent1、agent2 分别查询 | 均为 200 |
| agent1 接单但未带 CSRF token | 403 |
| agent1 携带正确 token 接单，即使伪造 assigneeId=2002 | 204，实际处理人仍为 2001 |
| agent1 重复接单 | 409 |
| agent2 查询或接单这张已分配给他人的工单 | 404 |
| alice 取消这张已接单工单 | 409 |
| agent1、alice 查询最终工单 | 均为 200，状态 IN_PROGRESS |

404 表示不存在或对当前身份不可见；409 表示可见但当前状态不允许操作。真正并发时，失败请求可能在可见性检查时得到 404，或者先读到 OPEN、随后条件更新失败得到 409。无论哪种情况，都不能返回成功或写入第二条 CLAIM。

脚本使用 Session 和 CSRF，登录后刷新 token；缺少 token 的负例会显式移除 WebSession 保存的请求头。脚本最后退出会话，保留工单供核对。脚本验证顺序请求；真正同时抢单由上面的并发测试验证。

## 5. 在 DBeaver 核对数据

连接本机 ticket_lab，把两处 123 改成脚本输出的新工单编号。分别选中并执行完整 SQL：

~~~sql
SELECT id, title, creator_id, assignee_id, status
FROM ticket_lab.tickets
WHERE id = 123;

SELECT id, ticket_id, actor_id, action, created_at
FROM ticket_lab.ticket_events
WHERE ticket_id = 123
ORDER BY id;
~~~

预期第一条结果 creator_id = 1001、assignee_id = 2001、status = IN_PROGRESS；第二条只有一条 actor_id = 2001、action = CLAIM 的记录。失败的接单和取消请求不应产生成功事件。

## 6. 能解释这段 SQL，就理解了接单竞争

~~~sql
UPDATE tickets
SET status = 'IN_PROGRESS', assignee_id = ?
WHERE id = ?
  AND status = 'OPEN'
  AND assignee_id IS NULL;
~~~

先 SELECT 只能知道读取那一刻的状态，不能阻止另一个请求接单。状态和未分配条件必须写在 UPDATE 的 WHERE 中；业务代码只有在更新行数为 1 时才继续插入 CLAIM。更新和插入记录共用一个事务，后一步失败时，前一步一起回滚。

代码阅读顺序：TicketController.claim → TicketService.claim → TicketMapper.claimOpenTicket → mapper/TicketMapper.xml → TicketEventMapper。CurrentUser 提供身份，SecurityConfig 限制角色，TicketClaimTests 验证业务结果。

完成标准：测试成功、脚本状态码全部符合预期、DBeaver 中处理人和单条 CLAIM 记录正确。通过之后再进入完成工单（IN_PROGRESS → RESOLVED）的练习。
