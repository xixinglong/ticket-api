# 02 练习笔记：接口验证、单元测试与字段扩展

第 02 课的重点是：用请求验证接口行为，用测试验证业务规则，再独立增加一个字段，把输入、处理、保存和输出串起来。完成标准是能够重复验证并解释结果。

课程来源：[[02 第一个 Java 接口：创建与查询工单]]。本笔记结合 2026-10-30 的练习整理，代码示例按已经增加 `description` 的项目版本编写。

实际工程目录：`C:\xixl-study\java-labs\ticket-api`。原课程示例使用 `C:\java-labs\ticket-api`，执行命令时应使用自己的实际路径。

## 一、先知道自己在验证哪一层

```text
HTTP 请求（JSON）
  → TicketController：接收参数、触发校验、决定 HTTP 响应
  → TicketService：检查业务规则、生成编号、保存或查询内存数据
  → TicketResponse：作为响应数据返回给调用方
```

| 文件或目录 | 作用 | 本课需要理解的内容 |
|---|---|---|
| `CreateTicketRequest.java` | 接收创建请求 | `title`、`description` 如何从 JSON 进入 Java |
| `TicketController.java` | 提供 HTTP 接口 | POST 创建、GET 查询、201 和 404 从哪里返回 |
| `TicketService.java` | 处理业务和内存数据 | 标题校验、编号生成、保存、查询 |
| `TicketResponse.java` | 表达响应数据 | 返回的 JSON 为什么有这些字段 |
| `src/main/java` | 主代码目录 | 放上述业务代码和启动类 |
| `src/test/java` | 测试代码目录 | 放 JUnit 测试，不能放到主代码目录 |

两种验证各有用途：

- HTTP 请求验证：请求能否被解析、参数校验是否生效、状态码和响应内容是否正确。
- Service 单元测试：直接调用 Java 方法，验证标题规则、保存和查询行为，不验证 HTTP 状态码。

## 二、接口验证：跑通四种场景

### 1. 启动服务

在工程根目录执行：

```powershell
Set-Location 'C:\xixl-study\java-labs\ticket-api'
.\mvnw.cmd spring-boot:run
```

看到 `Started TicketApiApplication` 后，保持服务窗口运行，另开一个 PowerShell 窗口发送请求。IDEA 和 PowerShell 选择一种方式启动，避免两个实例同时占用 8080。

### 2. 创建工单，检查 201 和响应内容

以下命令在发送请求的窗口中执行。使用英文示例，便于专注验证接口流程。

```powershell
$base = 'http://127.0.0.1:8080'
$json = @{
    title = 'Login page is blank'
    description = 'Blank after signing in'
} | ConvertTo-Json

$created = Invoke-WebRequest -UseBasicParsing -Method Post `
    -Uri "$base/api/tickets" `
    -ContentType 'application/json' -Body $json

$created.StatusCode
$ticket = $created.Content | ConvertFrom-Json
$ticket
```

验收结果：

- 状态码是 `201`。
- 返回 `id`，后续查询使用这个值，不写死为 `1`。
- `title` 是 `Login page is blank`，`status` 是 `OPEN`。
- `description` 是 `Blank after signing in`。

### 3. 查询刚创建的工单，检查 200 和数据一致性

```powershell
$queried = Invoke-WebRequest -UseBasicParsing -Method Get `
    -Uri "$base/api/tickets/$($ticket.id)"

$queried.StatusCode
$found = $queried.Content | ConvertFrom-Json
$found
```

验收结果：状态码是 `200`，编号、标题、状态、描述与创建时一致。

如果只想快速看响应内容，也可以用：

```powershell
Invoke-RestMethod -Method Get -Uri "$base/api/tickets/$($ticket.id)"
```

本课使用 `Invoke-WebRequest` 查看状态码，再通过 `ConvertFrom-Json` 读取内容；`Invoke-RestMethod` 则可以直接把 JSON 响应转换为对象。

### 4. 查询不存在的编号，检查 404

```powershell
try {
    Invoke-WebRequest -UseBasicParsing `
        -Uri "$base/api/tickets/not-found" -ErrorAction Stop
} catch {
    if ($null -ne $_.Exception.Response) {
        [int]$_.Exception.Response.StatusCode
    } else {
        $_.Exception.Message
    }
}
```

预期输出 `404`。如果输出连接失败等信息，说明没有取得预期的 HTTP 响应，应检查服务是否启动、地址和端口是否正确。

### 5. 提交纯空格标题，检查 400

```powershell
try {
    Invoke-WebRequest -UseBasicParsing -Method Post `
        -Uri "$base/api/tickets" -ContentType 'application/json' `
        -Body '{"title":"   "}' -ErrorAction Stop
} catch {
    if ($null -ne $_.Exception.Response) {
        [int]$_.Exception.Response.StatusCode
    } else {
        $_.Exception.Message
    }
}
```

预期输出 `400`。本练习中 `description` 可省略，所以这里专门验证标题约束。

`@RequestBody` 负责读取请求体，`@Valid` 触发 `CreateTicketRequest` 上的 `@NotBlank`、`@Size` 校验。非法标题在请求校验阶段被拒绝；直接调用 Service 的测试则验证 Service 自身抛出的 `IllegalArgumentException`。不要把两种入口的表现混为一谈。

## 三、单元测试：让规则可以反复验证

测试文件：`src/test/java/com/example/ticket/TicketServiceTest.java`。

当前练习包含 7 个 Service 测试：

| 测试方法 | 场景 | 核心断言 |
|---|---|---|
| `createdTicketCanBeFound` | 创建后查询，标题两端有空白 | 标题被清理，状态为 OPEN |
| `blankTitleIsRejected` | 纯空格标题 | 抛出 IllegalArgumentException |
| `nullTitleIsRejected` | null 标题 | 抛出 IllegalArgumentException |
| `titleLongerThan100CharactersIsRejected` | 101 个英文字母 | 抛出 IllegalArgumentException |
| `missingTicketReturnsEmpty` | 查询不存在的编号 | Optional 为空 |
| `twoCreatedTicketsHaveDifferentIdsAndCanBeFound` | 连续创建两张工单 | ID 不同，分别能查到原工单 |
| `descriptionIsPreserved` | 创建时传入描述 | 创建响应和查询结果均保留描述 |

前两个来自课程示例，中间四个是课程要求独立补充的用例，最后一个来自字段扩展练习。

### 测试的基本写法

每个测试按“准备数据 → 调用方法 → 断言结果”组织。每个方法新建 `TicketService`，避免依赖其他测试留下的内存数据和编号。

```java
@Test
void descriptionIsPreserved() {
    TicketService service = new TicketService();

    TicketResponse created =
            service.create("Login page is blank", "Blank after signing in");
    TicketResponse found = service.find(created.id()).orElseThrow();

    assertEquals("Blank after signing in", created.description());
    assertEquals("Blank after signing in", found.description());
}
```

| 写法 | 含义 |
|---|---|
| `assertEquals(expected, actual)` | 实际值与预期值一致 |
| `assertNotEquals(a, b)` | 两个值不同 |
| `assertTrue(condition)` | 条件为真 |
| `assertThrows(IllegalArgumentException.class, () -> ...)` | 调用时应抛出指定异常 |
| `optional.orElseThrow()` | 有值就取出，没有则抛异常，使测试失败 |

### 执行与判断

在工程根目录执行：

```powershell
.\mvnw.cmd test
```

预期 `TicketServiceTest` 为 7 个测试通过。若工程自带的 `TicketApiApplicationTests` 仍只有 1 个启动测试，总计应为 8 个，且 `Failures: 0`、`Errors: 0`、`Skipped: 0`，最后显示 `BUILD SUCCESS`。

这些数字是当前代码对应的预期，是否通过以实际运行输出为准。`spring-boot:run` 日志里的 `testCompile` 只表示编译测试代码，不能据此认定测试已经执行通过。

## 四、字段练习：增加 description

本次练习约定：描述可省略，省略时为 `null`；提供时原样保存。标题原有校验规则保持不变。

修改顺序：

1. `CreateTicketRequest`：增加 `String description`，让请求能够接收它。
2. `TicketResponse`：增加 `String description`，让响应能够返回它。
3. `TicketService.create`：改为 `create(String title, String description)`，构造响应对象时保存描述。
4. `TicketController`：改为调用 `service.create(request.title(), request.description())`。
5. 旧测试：所有创建调用都补齐第二个参数，无描述的场景传 `null`。
6. 新测试：增加 `descriptionIsPreserved`，验证创建和查询都保留描述。
7. 执行测试，再重启服务，用带描述的 JSON 创建和查询工单。

调用方式的变化：

```java
// 增加字段之前
service.create("Broken page");

// 增加字段之后：原有测试可以不提供描述
service.create("Broken page", null);

// 验证新字段
service.create("Broken page", "Blank after signing in");
```

`find()` 不需要为描述增加独立处理，因为 Map 保存的 `TicketResponse` 已经包含它。修改方法签名后，要同步检查所有调用处。

## 五、这次练习遇到的三个问题

| 现象 | 原因 | 处理方式 | 记住什么 |
|---|---|---|---|
| `nvoke-RestMethod` 无法识别 | 命令开头少写了 `I` | 改为 `Invoke-RestMethod` | 命令没有执行成功时，先检查拼写 |
| `org.junit.jupiter.api` 不存在，`Test`、`assertEquals` 等报错 | 测试文件误放到 `src/main/java` | 移到 `src/test/java/com/example/ticket` | 测试依赖的 scope 是 test，测试代码应放在测试目录 |
| `Port 8080 was already in use` | 排查时发现 IDEA 已启动本项目，再从 PowerShell 启动产生冲突 | 在 IDEA 停止原实例，再从选定入口启动 | 重启前确认旧实例已停止 |

排查时先找日志中具体的失败原因。最后一行 `BUILD FAILURE` 只是失败结果，本次端口冲突应看 `Port 8080 was already in use`，不能据此判断测试代码有问题。
