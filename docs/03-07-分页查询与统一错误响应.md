# 03-07-分页查询与统一错误响应

本节有两个目标：列表只返回当前人可见的一页数据；失败响应有稳定的结构，便于脚本和日志排查。截至 2026-10-31，相关新增代码与测试已编写，尚未运行本轮测试，不要把以下预期当作实测结果。

## 1. 接口合同

GET /api/tickets?page=1&size=20，page 从 1 开始，size 范围 1–100。省略参数时使用 1 和 20。

~~~json
{
  "items": [{"id":"123","title":"示例工单","status":"OPEN","description":null}],
  "page": 1,
  "size": 20,
  "total": 1
}
~~~

这是结构示意。items 是当前页，total 是当前人全部可见工单数量，不是数据库总工单数。没有数据时 items=[]、total=0；超出最后一页时 items=[]，total 仍可大于 0。

## 2. 从 Controller 一路读到 SQL

TicketController.list 接收 int 参数；TicketService.list 验证数值边界并计算偏移量；TicketMapper 先 countVisible 再 findVisible；TicketPageResponse 返回四个字段。

~~~java
long offset = ((long) page - 1) * size;
~~~

page=1,size=20 时 offset=0；page=2 时 offset=20。先转 long 再乘，避免大页码在 int 内计算时溢出。不能先用 int 乘完再强转。

COUNT 和分页查询共用 XML 中 visibleCondition：USER 只看 creator_id=自己；AGENT 看未分配 OPEN 或 assignee_id=自己。先按权限过滤，再排序分页。若先拿所有人数据再在 Java 删除不可见行，会漏页，也可能通过 total 泄露他人数据规模。

排序固定 ORDER BY id DESC。不要省略排序后声称第一页和第二页稳定；也不要把用户输入直接拼成排序 SQL。

## 3. 为什么列表加只读事务

count 和 items 是两次查询。同一次请求中，希望它们读取同一个可重复读快照；Service 使用 readOnly=true 和 REPEATABLE_READ。

这只约束一次请求。用户先查第一页，别人又创建数据，随后查第二页，偏移量分页仍可能出现重复或遗漏。这是当前实现的边界；需要跨请求快照或游标时再设计新契约，不能用本注解宣称完全解决。

## 4. 验证分页

服务启动后在 B 执行：

~~~powershell
.\scripts\Test-TicketPagination.ps1
~~~

按提示输入四个账号密码。脚本创建练习数据，检查分页、排序、角色可见性和参数边界，并保留数据供核对。数据库已有旧数据时，总数不应硬编码成刚创建的数量。

也可以复用登录模块的 aliceSession：

~~~powershell
$page = Invoke-RestMethod -Uri "$base/api/tickets?page=1&size=5" -WebSession $aliceSession
$page.items
$page | Select-Object page, size, total
~~~

应检查 page=0、size=0、size=101、page=abc 返回 400；未登录先返回 401。因为安全检查在参数绑定前，不能要求未登录请求先得到参数错误。

## 5. 统一错误响应怎么实现

新增 ApiError 保存 code、message、requestId。RequestIdFilter 在安全过滤器之前生成 UUID，并放进响应头 X-Request-Id。ApiExceptionHandler 将 MVC 参数错误、业务异常与未预期异常映射为 JSON；SecurityConfig 处理更早发生的登录、角色与 CSRF 错误，使用相同字段。

~~~json
{
  "code": "TICKET_CONFLICT",
  "message": "工单状态已变化，请重新查询后操作",
  "requestId": "示意编号，运行时为服务端生成的UUID"
}
~~~

| HTTP | code 示例 | 含义与处理 |
| --- | --- | --- |
| 400 | INVALID_REQUEST | 检查标题、JSON、数字参数 |
| 400 | INVALID_PAGINATION | page 或 size 超出约定范围 |
| 401 | UNAUTHENTICATED | 重新登录，检查会话 |
| 403 | FORBIDDEN | 检查角色和 CSRF，不能反复盲目重试 |
| 404 | TICKET_NOT_FOUND | 工单不存在或不可见 |
| 409 | TICKET_CONFLICT | 重新查询状态再决定动作 |
| 415 | UNSUPPORTED_MEDIA_TYPE | 使用接口要求的 Content-Type |
| 500 | INTERNAL_ERROR | 记录 requestId，在服务端日志排查 |

框架错误还可能有 NOT_FOUND、METHOD_NOT_ALLOWED、REQUEST_REJECTED。安全策略会先拒绝未开放的路由和方法，因此并非所有错误 URL 都会到达 MVC 的 404/405 处理器；401/403 的优先级以安全链为准。

统一结构覆盖本项目安全链和 MVC 异常；容器在进入应用过滤器之前拒绝的请求不属于这份承诺。

## 6. 为什么不直接返回 exception.getMessage()

数据库异常可能包含 SQL、连接信息，程序异常可能带内部类名。对客户端返回固定可读提示，内部错误的堆栈记录在服务端，并带 requestId。排查时用编号定位，不把完整内部日志放进接口响应或分享给无关人员。

本次请求编号由服务端生成，不直接反射客户端传入的 X-Request-Id。响应体与响应头应一致。正常成功响应体保持原结构，不强行套错误对象。

## 7. 新测试与练习

ApiExceptionHandlerTests 使用 MockMvc 和模拟 Service，不连接数据库，覆盖 404、409、分页400、非法 JSON、空白标题、415、500 脱敏与请求编号。TicketSecurityTests 增加安全错误字段断言与 /api/me 不返回密码的断言。分页有数据库与单元测试两个层次。

练习：page=abc 与 page=0 分别在哪里失败？参考：前者在 MVC 把字符串转成 int 时失败，Service 不会执行；后者能转换为 int，进入 Service 后被范围校验拒绝。
