## 接口约定

~~~text
GET /api/tickets?page=1&size=20
~~~

| 参数或字段 | 约定 |
| --- | --- |
| page | 从 1 开始，默认 1，最大 2147483647 |
| size | 默认 20，范围 1–100 |
| items | 本页可见工单，固定按 id DESC 排序 |
| total | 当前身份可见工单总数，不是整张表的数量 |
| 越过末页 | 返回 200、空 items，保留真实 total |
| 非法数字、负页码、size 越界 | 返回 400 |
| 未登录 | 返回 401 |
| 非 USER/AGENT 角色 | 返回 403 |

返回示例（编号和数量仅作格式演示）：

~~~json
{
  "items": [
    {"id": "87", "title": "Example ticket", "status": "RESOLVED", "description": "Example"}
  ],
  "page": 1,
  "size": 20,
  "total": 1
}
~~~

USER 可看到自己创建的全部状态工单。AGENT 可看到未分配的 OPEN 工单，以及分配给自己的工单（包括 RESOLVED）。已取消且未分配的工单不对处理人展示。列表与详情使用同一业务规则。

creatorId、actorId、userRole、sort 都不是本接口支持的参数，传入它们不会改变身份、数据范围或固定排序。

## 第二个 PowerShell 窗口运行验证脚本

服务启动成功后执行：

~~~powershell
Set-Location 'C:\xixl-study\java-labs\ticket-api'
.\scripts\Test-TicketPagination.ps1
~~~

依次输入 alice、bob、agent1、agent2 的应用登录密码。脚本记录四人的初始可见总数，新建以下五张工单并保留数据：

| 样本 | 创建人 | 处理人 | 最终状态 |
| --- | --- | --- | --- |
| Alice open | alice | 空 | OPEN |
| Bob open | bob | 空 | OPEN |
| Alice cancelled | alice | 空 | CANCELLED |
| Alice resolved | alice | agent1 | RESOLVED |
| Bob assigned | bob | agent2 | IN_PROGRESS |

相对于脚本运行前，可见总数应分别增加：alice 3、bob 2、agent1 3、agent2 3。已有工单会保留，因此不要把数据库总数写死为 5。

脚本遍历各账号可见列表，检查本次样本的包含/排除、total、编号倒序、相邻页不重叠，并验证伪造参数和超大页码。它还打印可直接执行的 DBeaver SQL，供核对这五张工单。

运行期间先暂停其他创建、接单或取消操作。脚本检查不同请求之间的数据稳定性；若同时修改数据，总数可能变化，脚本会提示重试。脚本最多读取 1000 页，每页 100 条，用于本地练习。

## 在 DBeaver 理解查询

选择本机 ticket_lab，以下示例对应 alice 的第一页和总数：

~~~sql
SELECT id, title, creator_id, assignee_id, status
FROM ticket_lab.tickets
WHERE creator_id = 1001
ORDER BY id DESC
LIMIT 20 OFFSET 0;

SELECT COUNT(*) AS total
FROM ticket_lab.tickets
WHERE creator_id = 1001;
~~~

agent1 的可见范围：

~~~sql
SELECT id, title, creator_id, assignee_id, status
FROM ticket_lab.tickets
WHERE (status = 'OPEN' AND assignee_id IS NULL)
   OR assignee_id = 2001
ORDER BY id DESC
LIMIT 20 OFFSET 0;
~~~

这些 SQL 固定使用练习账号编号，只为 DBeaver 观察。应用代码中的编号必须来自登录会话，不能照抄成固定值。

## 关键实现与限制

偏移量按 ((long) page - 1) * size 计算，乘法前转 long，避免 int 溢出。Mapper 通过参数绑定传递 size 和 offset，不拼接用户输入。总数和分页查询共用 XML 中的权限条件，避免一个过滤而另一个泄露数据。

Service 使用 REPEATABLE_READ 的只读事务，让同一次响应中的 COUNT 和 SELECT 使用同一个数据库快照。两个不同翻页请求仍是不同事务：如果期间有新建或可见性变化，OFFSET 分页可能出现跨请求重复或遗漏；固定排序不等于锁住整个翻页过程。

本阶段使用课程要求的 LIMIT/OFFSET，不增加自定义排序或游标。很深的分页和处理人 OR 查询的性能尚未用代表性数据及 EXPLAIN 验证，不宣称已经优化，也不额外创建索引。

代码阅读顺序：TicketController.list → TicketService.list → TicketMapper.countVisible/findVisible → TicketMapper.xml 的 visibleCondition。响应结构见 TicketPageResponse。
