# 03-11-数据库用户模块：登录、密码哈希与数据关联

本节承接 [[03-04-登录权限与Session练习]]、[[03-02-MySQL表结构与SQL练习]]。原课件中的固定练习账号是前一阶段的实现；本节讲解如何在保持工单接口不变的前提下，将身份来源迁移到数据库。

本文只讲公共知识、当前代码与练习，不记录某台电脑的测试进度。具体迁移操作见 [[03-用户模块实施与双机迁移记录]]。不要直接在业务库执行本节的修改练习。

## 1. 学完应能解释什么

- 为什么工单已经存进数据库，还需要单独的用户表？
- 用户提交密码后，谁查数据库、谁校验密码、谁保存登录状态？
- 为什么密码哈希不能直接用字符串相等来校验？
- 外键、角色权限、工单归属分别解决什么问题？
- 为什么禁用用户后，已经登录的浏览器可能仍能访问？
- 迁移为什么要保留用户编号，而且不能认为整个过程会自动回滚？

本阶段不包含注册、找回密码、用户管理页面、复杂多角色模型或会话即时撤销。

## 2. 从固定账号到数据库账号

旧实现根据用户名进入固定分支，构造 alice、bob、agent1、agent2 四个身份对象。它适合先学习 Session 和权限，但新增账号必须改代码，而且工单里的用户编号没有数据库层面的关联保证。

新版让 UserDetailsService 调用 UserMapper，从 users 表查询账号，再构造 TicketUser。Controller 的创建、查询、取消、接单和完成接口不需要因此改变。

这里有两套不同账号：

| 账号 | 谁使用 | 用途 |
| --- | --- | --- |
| 数据库账号，例如 ticket_app | 后端连接池 | 连接 MySQL、执行授权范围内的 SQL |
| 应用账号，例如 alice | 浏览器或 API 客户端 | 登录工单应用，获得 USER 或 AGENT 身份 |

把 alice 的登录密码填进 DB_PASSWORD，并不能让应用连接数据库；把数据库口令提交给 `/api/login`，也不是应用登录方式。

## 3. 用户表怎么读

完整定义在项目 `sql/02-users.sql`。字段不是越多越好，当前只保存登录和关联所需的信息。

| 字段 | 作用 | 注意点 |
| --- | --- | --- |
| id | 稳定的业务用户编号 | 当前不自增，迁移时显式保留已有编号 |
| username | 唯一登录名 | 使用 utf8mb4_bin 排序规则，区分大小写 |
| password_hash | 密码哈希 | 使用带 `{bcrypt}` 前缀的编码，不保存明文 |
| role | 当前单一角色 | CHECK 限定为 USER 或 AGENT |
| enabled | 是否允许新登录 | 只能为 0 或 1，不等于撤销所有已有会话 |
| created_at | 用户创建时间 | 默认由数据库写入，保留微秒精度 |

用户名唯一约束防止重复登录名；角色 CHECK 防止写入不支持的角色。MySQL 需要 8.0.16 或更高版本才能真正执行 CHECK 约束。

表和字段的 COMMENT 是给维护者看的说明，不会自动产生 Java 校验规则。备注写着“密码哈希”，数据库也不会自动替你加密输入。

`CREATE TABLE IF NOT EXISTS` 只在表不存在时创建表，不会修正旧表的字段定义或备注。已有表补备注使用 `sql/03-users-comments.sql`，执行前仍应核对实际表结构。

## 4. 一次登录经过哪些代码

```text
客户端获取 /api/csrf，保存 Cookie 与 token
  -> POST /api/login，提交表单 username/password 及 CSRF token
  -> Spring Security 表单登录过滤器
  -> 认证提供者调用 UserDetailsService
  -> UserMapper 查询 users
  -> UserRow 转为 TicketUser
  -> 校验账号状态与密码
  -> 成功后保存认证上下文到 Session，返回 204
```

`/api/login` 由 Spring Security 处理，不是 AuthController 中手写的登录方法。成功后客户端应在同一 Cookie 会话中重新获取 CSRF token，因为认证成功会清除旧 token。

关键代码阅读顺序：

1. `src/main/java/com/example/ticket/UserRow.java`：数据库查询结果的数据载体。
2. `UserMapper.java`：按用户名查询，`#{username}` 使用参数绑定，不拼接用户输入。
3. `SecurityConfig.java`：提供 PasswordEncoder 和 UserDetailsService，配置登录、退出及访问规则。
4. `TicketUser.java`：在 Spring Security 的 User 上增加业务 id，并传入 enabled 与角色。
5. `AuthController.java`：提供 CSRF token 和当前身份接口，身份响应不返回密码哈希。
6. `CurrentUser.java`：业务层从认证上下文获取身份，不信任请求里的用户编号。

UserMapper 查询中的 `password_hash AS passwordHash` 是列别名，用于对应 Java 字段名称。不要把“Java 使用驼峰字段名”理解成数据库必须改成同样的列名。

## 5. BCrypt 校验的正确理解

本项目通过 `PasswordEncoderFactories.createDelegatingPasswordEncoder()` 创建编码器，默认编码结果采用 BCrypt，并带有 `{bcrypt}` 算法标识。

```java
PasswordEncoder encoder = PasswordEncoderFactories.createDelegatingPasswordEncoder();
String encoded = encoder.encode("example-only-password");
boolean correct = encoder.matches("example-only-password", encoded);
```

示例口令只用于理解 API，不用于真实账号。实际代码不要打印原始密码或完整哈希。

BCrypt 使用随机盐，因此同一密码调用两次 encode，通常得到不同字符串。验证时使用 matches，让编码器根据已有哈希中的信息进行校验；不能重新 encode 后比较两个字符串。

密码哈希不是可解密的密码存档。忘记密码应通过可靠的重置流程处理，不是从数据库“解密找回”。哈希也仍然属于敏感信息，泄漏后可能被离线猜测，因此接口和日志不应返回它。

数据库中的哈希若缺少 DelegatingPasswordEncoder 所需的算法前缀，认证可能失败。不要通过改成 `{noop}` 或保存明文来解决配置问题。

## 6. 登录之后，权限从哪里来

数据库 role 为 USER 时，TicketUser 构造 `ROLE_USER` 权限；AGENT 对应 `ROLE_AGENT`。这是 Spring Security 的角色命名约定，不要求把数据库值也改成带 ROLE_ 的形式。

登录成功后，后续请求主要从 Session 恢复认证身份，不是每次请求都重新查询 users。业务代码用 CurrentUser 获取 TicketUser，再依据其 id 和角色过滤工单。

三个检查层次不能相互替代：

| 检查 | 例子 | 不能替代的事情 |
| --- | --- | --- |
| 已认证 | 请求带有效登录会话 | 不能保证有权执行接单 |
| 角色授权 | USER 不能调用 AGENT 接单接口 | 不能保证处理人有权操作任意工单 |
| 数据归属和状态 | 只有本人负责且 IN_PROGRESS 的工单可完成 | 不能靠前端隐藏按钮实现 |

接口不接受客户端指定当前操作者。即使请求提交 creatorId 或 actorId，服务端也必须使用认证身份确定写入人。

## 7. 用户外键解决什么问题

```text
tickets.creator_id  -> users.id
tickets.assignee_id -> users.id（未接单时允许 NULL）
ticket_events.actor_id -> users.id
```

迁移工具增加上述三个外键，原有 `ticket_events.ticket_id -> tickets.id` 外键继续保留。

外键让数据库拒绝不存在的用户编号，并阻止直接删除仍被工单或事件引用的用户，避免历史记录失去关联。通常先禁用账号，而不是删除它。

但外键不能证明 assignee_id 一定是 AGENT，也不能判断某人能否取消这张单。这些规则仍由业务层验证。数据库约束与业务权限是在不同层面共同保护数据。

## 8. 禁用不等于立即踢下线

将 enabled 改为 0 后，新登录会被拒绝。但已经保存到 Session 的 TicketUser 是登录时取得的身份，当前实现不会逐请求重新读取 enabled。

因此存在以下行为：

- 禁用账号：阻止后续登录，已有会话可能继续有效。
- 修改密码：下一次登录使用新密码，旧会话不会自动失效。
- 修改角色：已有会话仍可能持有旧角色，重新登录才取得新角色。
- 退出登录：使当前会话失效，不代表其他浏览器的会话同时失效。

本项目使用单实例内存 Session，重启服务会使已有会话失效。它是当前练习环境的处理手段，不是通用生产方案。若要求禁用立即生效，需要另行设计会话撤销、用户状态版本检查等机制，并补充跨会话测试。

## 9. 旧数据迁移为何要单独设计

已有工单引用 1001，不代表可以给 alice 新生成一个任意 id。迁移必须保留 1001/1002/2001/2002 与四个账号的对应关系，否则旧工单可能变成无人拥有，甚至关联错误的人。

`scripts/MigrateUsers.java` 的处理顺序：

1. 检查业务表里的用户编号，遇到预设映射以外的编号就停止，交由人工确认。
2. 读取初始化密码并生成哈希，创建 users 表。
3. 检查已有账号映射；插入缺少的账号，已有账号不重置密码或 enabled。
4. 提交账号写入事务后，检查并添加缺少的用户外键。

这是四个练习账号的迁移工具，不是适用于任意数据的自动修复器。不要为了让它通过而随意修改旧编号、删除记录或关闭外键检查。

MySQL DDL 会隐式提交，创建表、添加外键不能与所有账号写入一起获得完整事务回滚。迁移失败时可能已经留下表或部分外键。应先停写、备份，出错后检查现场，再修正原因重试。

这里的 LAB_* 密码变量只用于初始化工具，不再是新版服务的登录配置。仅修改环境变量不会更改已有数据库用户密码。

## 10. 动手练习

先准备已完成用户初始化的独立练习库，确认连接指向正确的库。不要使用业务库，更不要把测试口令写入业务账号。

### 练习一：阅读结构，不读取密码

```sql
SELECT DATABASE();
SHOW CREATE TABLE users;
SELECT id, username, role, enabled, created_at FROM users ORDER BY id;
```

指出主键、唯一约束、CHECK、表备注和字段备注的位置。解释为什么这条 SELECT 没有包含 password_hash。

### 练习二：追踪一次真实登录

使用现有客户端先获取 CSRF，再提交表单登录，最后请求 `/api/me`。观察 204 登录响应、Session Cookie，以及只含身份信息的 `/api/me` 响应。

说明：哪个步骤查询 users，哪个步骤校验密码，为什么登录成功后要重新获取 CSRF token。不要把密码写入共享截图、日志或命令历史。

### 练习三：验证账号禁用边界

在独立库中，用一个浏览器会话登录 alice，再将其 enabled 改为 0。保留原会话，同时使用一个全新会话尝试登录。应分别观察旧会话和新登录，不要混为同一个测试。

记录观察结果后恢复 enabled=1，并退出测试会话。预期新登录失败；当前实现中的旧会话不保证立即失效。

### 练习四：证明是数据库身份，而非固定分支

阅读 `DatabaseUserTests.newlyInsertedUserCanLoginWithoutCodeChanges`：测试在事务中插入新用户，用 PasswordEncoder 生成哈希，再通过真实安全过滤器登录。

解释这个测试为什么比“alice 仍能登录”更能证明固定账号分支已被替换，以及测试事务回滚为什么适合清理该样本。

### 练习五：观察外键拒绝非法引用

阅读 `DatabaseUserTests.foreignKeysProtectAllUserReferences`，分别解释创建人不存在、处理人不存在、事件操作者不存在和删除被引用用户为什么失败。

再思考：一个存在的 USER 编号写入 assignee_id，外键是否一定拒绝？答案是否定的，角色规则需要应用层检查。

## 11. 测试与排错

测试类位于 `src/test/java/com/example/ticket/DatabaseUserTests.java`；旧权限、事务、并发与分页测试也要一起运行。测试库需先完成 users 初始化与外键迁移，不能只创建 tickets 和 ticket_events。

| 现象 | 优先检查 |
| --- | --- |
| users 表不存在 | 是否只执行旧建表脚本，是否连接错库 |
| 固定账号无法登录 | 初始化是否完成、密码是否对应该库、enabled 是否为 1 |
| 旧密码仍有效，新环境变量无效 | 已有哈希不会被重复迁移或环境变量覆盖 |
| 用户查询正常但密码失败 | 哈希格式和算法前缀是否完整，是否误存明文 |
| 分页样本插入被外键拒绝 | 测试是否只造了身份对象，却没插入对应 users 记录 |
| 禁用后旧浏览器仍可访问 | 是否仍使用已经认证的 Session |
| 数据库故障时登录返回 401 | 当前统一登录失败响应不区分底层原因，结合 requestId 查服务端日志 |

数据库不可用也可能导致新登录失败，不能仅凭客户端的 401 判断一定是用户输错密码。日志用于定位，但不应把数据库异常或口令返回给客户端。

- 能画出从登录表单到 UserMapper、PasswordEncoder、Session 的流程。

- 能演示数据库新增账号无需修改固定登录分支即可登录。
- 能验证错误密码、未知账号、禁用账号均无法成功登录。
- 能验证三个用户外键，同时解释外键不代替角色与归属校验。
- 能说明旧数据编号保留、重复迁移和 DDL 非整体回滚的边界。
- 在自己的独立测试库运行完整回归，保留代码版本、环境和结果；另一台电脑分别验收。

面试复述可以从这段话开始，再用代码解释：

> 我将登录身份从固定账号迁移到 MySQL，通过 MyBatis 提供 UserDetailsService 的查询结果，由 Spring Security 校验密码和账号状态。密码使用 BCrypt 哈希，工单关联稳定的用户主键。角色与工单归属仍在服务端检查。当前 Session 保存的是登录时身份，因此禁用账号只阻止新登录，立即撤销已有会话是另一个需要设计的能力。
