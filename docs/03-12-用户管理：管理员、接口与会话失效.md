# 用户管理：管理员、接口与会话失效

## 1. 本课目标

上一课把登录用户从内存移入数据库。本课解决另一个问题：账号已经在数据库里，怎样通过受保护的接口创建、查询、启停和重置密码？

完成后，你应该能解释角色与数据库账号的区别，读懂 Controller → Service → Mapper 的调用过程，并用两个独立会话验证旧登录状态是否失效。

本课在上一课基础上新增认证版本号。上一课“禁用只影响新登录”的描述属于当时实现；完成本课后，旧会话将在下一次请求时被拒绝。公共旧课件保留作为阶段学习材料。

## 2. 先定义权限

| 角色 | 工单能力 | 用户管理能力 |
| --- | --- | --- |
| USER | 创建、查看和取消自己的工单 | 无 |
| AGENT | 查看允许的工单、接单和完成 | 无 |
| ADMIN | 无，不自动兼任客服 | 查询账号，创建和管理 USER、AGENT |

管理员不是“所有接口都能访问”的万能角色。本课将账号管理与工单处理分开，避免为了管理用户而扩大工单访问范围。

管理员不能通过接口创建另一个管理员，也不能禁用或重置管理员账号。管理员由维护脚本初始化，避免自我锁定和接口提权。暂不提供角色修改、用户删除、自助注册、找回密码或前端页面。保留用户记录可以维持历史工单与操作记录的关联。

数据库连接用户仍只需运行时的 SELECT、INSERT、UPDATE、DELETE 权限。ADMIN 是 users.role 的业务角色，不等于 MySQL root，也不需要 DDL 权限。

## 3. 按调用顺序读代码

| 文件 | 重点 |
| --- | --- |
| SecurityConfig.java | 管理路径要求 ADMIN，/api/me 允许三种角色，保留 CSRF |
| CurrentUser.java | Service 再次检查 ADMIN；工单读取仍只允许 USER、AGENT |
| UserManagementController.java | 读取请求体与参数，设置 201 或 204 状态 |
| UserManagementService.java | 校验、密码哈希、事务及管理员保护 |
| UserMapper.java | 参数化 SQL、分页查询、更新版本号 |
| ManagedUserResponse.java | 只暴露编号、用户名、角色和启用状态 |
| AccountSessionFilter.java | 每个已登录请求对照数据库校验身份 |
| TicketUser.java | 登录时保存 authVersion，不依赖会被清除的密码字段 |

Controller 不直接写 SQL。Service 的权限检查也不能只依赖 Controller，因为以后定时任务或其他业务服务可能直接调用 Service。

列表通过重复读只读事务查询总数和当前页，按 id 倒序排序；偏移量先转 long 再乘，避免整数溢出。列表 SQL 不查询密码哈希，响应对象也没有该字段。

## 4. 接口契约

| 方法与路径 | 请求 | 成功响应 |
| --- | --- | --- |
| GET /api/admin/users?page=1&size=20 | page≥1，1≤size≤100 | 200，items/page/size/total |
| POST /api/admin/users | username、password、role | 201，新账号摘要 |
| PATCH /api/admin/users/{id}/enabled | enabled 布尔值，不能省略 | 204 |
| POST /api/admin/users/{id}/reset-password | password | 204 |

账号摘要中的 id 是字符串，保持与工单编号相同的对外约定。用户编号由 MySQL AUTO_INCREMENT 分配，不使用 MAX(id)+1；回滚后编号有空洞是正常现象。

创建请求示例，仅供独立练习库使用：

```json
{
  "username": "practice-user",
  "password": "practice-only-password",
  "role": "USER"
}
```

用户名为 3～64 位 ASCII 字符，首位为字母或数字，后续允许字母、数字、下划线、点和短横线；区分大小写，不自动去除空格。密码至少 12 个 Java 字符单位，UTF-8 编码不能超过 72 字节，不能全为空白，不自动裁剪。中文密码可能先达到字节上限，这是 BCrypt 的限制，不是数据库列长度不足。

重复用户名由数据库唯一键兜底，转换为 409 USERNAME_EXISTS。不能仅靠“先查是否存在”，因为并发请求可能同时查到不存在。缺少字段或非法参数返回 400；未登录返回 401；越权和 CSRF 失败返回 403；目标用户不存在返回 404。数据库内部异常不能直接作为响应返回。

## 5. 使用两个独立会话验证

可用 Postman 的独立 Cookie 容器或两个互不共享 Cookie 的客户端。不要把真实密码写进课件、请求集合或 Git。

1. 管理员客户端 GET /api/csrf，保存 Cookie 与返回的 headerName、token。
2. 在同一客户端 POST /api/login，使用表单 username、password，并携带 CSRF 请求头。
3. 登录成功后重新 GET /api/csrf。登录会更换 CSRF token，不能沿用登录前的值。
4. 管理员创建练习用户，记录返回 id；普通用户客户端登录该账号。
5. 普通用户 GET /api/me 应成功，GET /api/admin/users 应为 403。
6. 管理员 PATCH 对应 enabled 接口，发送 {"enabled":false}。写接口使用管理员自己的 Cookie 和 CSRF。
7. 普通用户带旧 Cookie GET /api/me，应返回 401；禁用期间重新登录也失败。
8. 管理员重新启用。旧会话不能复活，必须重新登录。
9. 管理员重置密码。已有多个会话都应在下一次请求被拒绝；旧密码登录失败，新密码登录成功。
10. 管理员分页查询，检查响应中没有 password、passwordHash、authVersion。

## 6. 为什么需要认证版本号

登录成功时，TicketUser 保存数据库中的 auth_version。每次使用已登录身份访问服务，过滤器查询当前账号，检查是否存在、启用状态、用户名、角色以及版本号。

```sql
UPDATE users
SET enabled = ?, auth_version = auth_version + 1
WHERE id = ? AND role IN ('USER', 'AGENT');
```

密码更新也在同一条 SQL 中递增版本号。业务修改与失效标记原子写入，不会出现“密码已改但版本未改”的中间结果。重复启用也会递增版本，属于保守撤销会话的设计。

只检查 enabled 不够：禁用后再启用，如果旧会话从未发过请求，它可能重新有效。版本号保证旧身份不再匹配。只比较密码字段也不可靠，Spring Security 通常会在认证后清除身份对象中的密码。

不匹配时清除安全上下文、使当前 Session 失效并返回 401。过滤器位于 CSRF 校验前，因此旧会话的写请求也先被身份检查拒绝。数据库暂时不可用则返回不带连接细节的 503，拒绝继续处理，但不销毁 Session，便于数据库恢复后重试。

这不是终止已经在执行的请求。一个请求通过校验后，另一个请求才禁用账号，前者仍可能完成。本课保证后续请求重新校验，不承诺并发事务的强制中断。每个已登录请求增加一次数据库查询，是本阶段的性能代价。

手工维护密码、角色或状态时必须同步递增 auth_version。直接改哈希但不递增版本不会撤销现有会话；绕开应用的维护操作也必须遵守协议。

## 7. 数据库升级与管理员初始化

不要让测试连接日常业务库。先在独立库完成以下流程，再按维护窗口升级业务库。

1. 新库执行 sql/01-schema.sql，再按上一课运行 scripts/MigrateUsers.java，建立四个初始用户及外键。已有库不重复初始化业务表。
2. 停止所有应用写入并备份，检查 SHOW CREATE TABLE users、tickets、ticket_events，确认处于上一课结构。
3. 执行一次 sql/04-user-management.sql。脚本临时移除三条用户外键，将用户主键改为自增、添加 ADMIN 与 auth_version，再重建外键。
4. 检查三条用户外键已重建、旧用户编号未变化、原业务行数未变化。不要使用 FOREIGN_KEY_CHECKS=0 跳过数据核对。
5. 用维护账号和私密环境变量运行 BootstrapAdmin.java；首次创建管理员，再次运行不会覆盖密码。若同名账号不是启用管理员，脚本拒绝执行。
6. 用受限数据库账号启动新版应用，重新登录，再验证接口。

准备 Java 脚本依赖：

```sh
./mvnw dependency:build-classpath -Dmdep.outputFile=target/migration-classpath.txt
java --class-path "$(cat target/migration-classpath.txt)" scripts/BootstrapAdmin.java
```

以上是 POSIX shell 示例，Windows 使用 mvnw.cmd，并用 PowerShell 读取 classpath。执行前从本机私密配置设置 DB_URL、DB_USER、DB_PASSWORD、ADMIN_USERNAME、ADMIN_PASSWORD；不要把密码直接写在可保存的命令行里。脚本只初始化，不承担管理员密码恢复。

04 是一次性迁移，不是幂等脚本。MySQL DDL 会隐式提交，中途失败不能依赖 ROLLBACK 恢复全部表结构。保持应用停止，检查实际结构和备份，再制定修复步骤；不要直接重新执行整份脚本。新版应用依赖 auth_version，不能未经升级直接替换旧应用。

旧版 sql/03-users-comments.sql 是上一阶段备注脚本，不要在 04 之后执行，以免把备注写回旧行为。旧版 MigrateUsers.java 是四账号迁移工具，也不是日常账号同步工具；系统已有新增用户及工单后不要再次运行它。

## 8. 测试与排错

UserManagementTests 使用真实 MySQL、真实登录与安全过滤器，测试修改通过测试事务回滚。AccountSessionFilterTests 单独模拟数据库不可用，验证拒绝访问而不泄露内部信息。scripts/verify-macos.py 在新建隔离库中打包、运行完整测试，再执行真实 HTTP 与重启验收。

| 现象 | 检查顺序 |
| --- | --- |
| Unknown column auth_version | 是否升级了实际 DB_URL 对应的库 |
| 管理员访问工单返回 403 | 正常权限边界，管理员不是客服 |
| 登录成功但写接口返回 403 | Cookie 是否一致，是否重新获取登录后的 CSRF |
| 重新启用后旧 Cookie 仍返回 401 | 正常，应重新登录 |
| 修改 id 报外键引用错误 | 是否按 04 顺序移除并重建用户外键 |
| BootstrapAdmin 拒绝同名账号 | 检查是否误用了普通用户名称，不自动提升其权限 |
| 请求返回 503 | 检查数据库连通性和服务端日志，不绕过身份校验 |

## 9. 练习与完成标准

1. 画出一个管理员重置密码请求经过的过滤器、Controller、Service、Mapper 和 SQL。
2. 使用两个普通用户会话，验证一次重置让两个旧会话都失效。
3. 在独立库测试禁用后立即启用，说明为什么仅检查 enabled 不足够。
4. 解释用户名唯一键如何处理并发创建，并说明为什么不能用 MAX(id)+1 分配编号。
5. 阅读管理接口响应 DTO，确认密码哈希不会通过列表或创建响应泄露。

完成标准：正常路径可用；USER、AGENT 无法管理账号；ADMIN 无法通过本接口提升权限或操作工单；旧会话按约定失效；业务外键完整；全部回归测试通过。测试通过不等于日常业务库已经升级，实际部署状态应另记在项目记录中。
