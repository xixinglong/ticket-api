# 05 Java 快速转岗：投递、复盘与 AI 学习法

转岗准备容易陷入两个极端：一边觉得还没学完，不敢投递；另一边只靠 AI 拼出项目，却讲不清代码。

**更可执行的做法，是让学习、项目和投递同时推进，但只在简历上写已经能够证明的能力。**

这篇给出执行办法，不预测招聘行情，也不承诺投递数量与录用结果之间有固定关系。

## 一、先选岗位，再决定补什么

第一周整理 10 个你确实愿意投递的岗位。地点、薪资预期、业务方向和工作方式不匹配的岗位，不要拿来扩大自己的学习清单。

每条岗位记录四件事：

- 主要工作是前端、Java 业务开发，还是两者都需要。
- Java 工作经验是否为硬性要求。
- 反复出现的必需技能。
- 自己能展示的证据和当前缺口。

把要求分成三类：

**已经能证明：** 例如前端工程化、复杂页面交付、接口联调。必须使用自己的真实经历。

**短期可以补齐：** 例如普通接口、SQL、业务校验、基础测试和部署。

**短期没有对应经历：** 例如多年 Java 生产故障治理、复杂分布式架构负责人经验。不要用一个学习项目冒充。

本计划优先考虑能利用已有前端能力、同时要求 Java 后端交付的岗位。是否适合某个职位，最终仍要看实际职责，不只看“全栈”两个字。

## 二、简历怎么表达才真实

保留 9 年前端经历。Java 学习项目单独列出，注明个人实战或学习项目，不把年限相加后写成“9 年 Java”。

不要写：

> 精通 Java 全栈，拥有高并发架构经验。

如果确实完成并验证了对应内容，可以改为：

> 9 年前端开发经验，具备 Java 后端实战能力。独立完成工单系统的接口、持久化、对象权限、事务及测试，能够进行前后端联调与部署。

项目描述可以使用这个骨架，但括号里的内容必须替换为真实证据：

> 为解决【具体问题】，实现【自己的职责范围】。针对【一个失败场景】，采用【具体方案】，通过【实际测试或演示】验证。

没有实际压测数据，就不写 QPS、并发用户规模或性能提升百分比。没有真实上线，就写本地或演示环境，不写生产落地。

## 三、什么时候开始投递

建议把求职准备提前，但不把未完成项目包装成已完成：

**第 1 周：** 整理目标岗位，确认哪些能力是共同要求。

**第 3 周：** 整理简历初稿和项目运行说明，标记尚未完成的内容。

**第 4 周起：** 如果已能讲清并演示核心业务，可先尝试少量匹配岗位。缺少关键权限或事务能力时，如实说明完成范围，不抢着宣称能独立上线。

**第 5–6 周：** 根据实际反馈调整投递与补课。不要因为某一次面试问到一个偏门知识，就立即改掉整个学习计划。

建议用下面的记录模板，每次只写真正有用的信息：

```text
岗位及日期：
主要职责：
重复出现的要求：
被追问的具体问题：
我回答不清的原因：
下一次要补的一个实验：
```

区分三种情况：不会概念、没有做过、做过但表达不清。它们对应的补救分别是小范围学习、补实验、练讲解，不必都重新刷一门课。

## 四、AI 只负责帮你缩短反馈时间

每次练习使用同一条工作流程：

1. 自己写出需求与验收条件。
2. 先尝试一个小实现，卡住时保留错误现场。
3. 给 AI 最小必要上下文，请它先解释原因。
4. 检查修改差异，拒绝无关重构和随意升级依赖。
5. 执行对应验证，再补一个失败场景。
6. 关闭答案，独立改一个相近需求。

这里没有“一定要坚持自己写多少分钟”的硬规定。关键是自己参与判断，而不是从一开始就复制整个工程。

### 不懂代码时这样问

> 我有前端经验，正在学 Java。请只解释下面方法的输入、返回值、可能异常，以及哪些地方改变了状态。遇到框架特性时，说明它在本例中的作用，不展开无关原理。最后给我一道变式练习，先不要给答案。

### 排错时这样问

> 下面是已经脱敏的最小代码、运行命令、依赖版本、实际报错和预期结果。请区分确定事实与猜测，先提出一个最值得验证的原因，再给最小修改。不要重写整个文件，不新增依赖，不跳过失败测试。

### 审查业务时这样问

> 请按输入校验、登录身份、对象权限、状态变化、并发竞争、事务回滚六项检查下面的工单取消实现。每项指出具体代码依据；信息不足就说缺少什么，不要仅凭出现注解就判定安全。最后列出三个最有可能失败的测试。

这些提示词不是安全认证。AI 的审查结论仍然要靠代码、测试和实际行为确认。

## 五、这四种状态不能混在一起

**代码已生成：** 只有文本，还没有执行证据。

**代码已检查：** 做过阅读或静态检查，不代表能编译。

**编译已通过：** 当前环境下能够构建，不代表业务正确。

**测试已通过：** 已执行的那些测试通过，不代表所有场景都正确。

记录时写明实际执行了什么。要求 AI 报告命令和结果，不接受没有执行证据的“应该没问题”。

本套笔记只完成文档编写和静态检查，没有替你创建练习工程、安装依赖、编译或运行测试。

## 六、不要把敏感资料作为提问材料

不要上传公司私有源码、客户数据、密钥、数据库密码、会话 Cookie 或访问 token。先使用虚构数据与最小复现；涉及公司资料时，遵守公司授权范围和工具使用规定。

日志脱敏也要保留足够的技术信息，例如异常类型、脱敏后的 SQL 结构和调用位置。只删掉报错内容再让 AI 猜，通常无法有效定位。

也不要在不理解用途的情况下执行 AI 给出的删库、重置权限、关闭安全防护或下载执行脚本命令。

## 七、给自己做一次最终验收

从下面选一个新需求，限时完成，但不设统一的就业门槛：

- 给列表增加状态筛选，拒绝未知状态。
- 给工单增加描述字段，补长度限制与测试。
- 为取消失败增加稳定错误码，保持原有权限规则。

验收时检查：

- [ ] 能先写清需求和边界，而不是直接生成代码。
- [ ] 能独立修改接口、业务、数据及测试。
- [ ] 没有为了通过正常场景而删掉权限或异常检查。
- [ ] 能解释每一个新增依赖和关键判断。
- [ ] 能演示一个成功场景和两个失败场景。

如果这些做得到，再根据目标岗位补缺。不要把“还有很多知识没学”当作无限推迟投递的理由，也不要把 AI 的产出当作自己已经掌握。
