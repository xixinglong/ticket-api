# 03-06-接单并发与完成流程详解

本节把工单从 OPEN 推进到 IN_PROGRESS，再到 RESOLVED，并解释两个处理人同时接单为什么只能有一个成功。先看 IDE 中的业务规则，运行验证时在 PowerShell B 操作，结果在 DBeaver 检查。

## 1. 接单与完成的业务合同

| 动作 | 角色 | 对象条件 | 成功后 | 事件 |
| --- | --- | --- | --- | --- |
| claim | AGENT | OPEN 且没有处理人 | IN_PROGRESS，处理人为当前人 | CLAIM |
| resolve | AGENT | IN_PROGRESS 且处理人为当前人 | RESOLVED，处理人保留 | RESOLVE |

请求不接收 assigneeId，不允许客户端决定由谁接单。用户 alice 创建后，agent1 接单与完成，事件的 actor_id 应为 2001；工单 creator_id 仍为 1001，不会被改成处理人。

AGENT 可见范围是“未分配的 OPEN”或“分配给自己”。另一个人接走后，它对其他 AGENT 不再可见。因此“另一人后来再接”可能是 404，而“我重复接自己已经接到的工单”是 409。

## 2. 并发错误怎样产生

假设只写 Java 检查，然后无条件 UPDATE：

~~~text
agent1 查询：OPEN
agent2 查询：OPEN
agent1 更新：处理人=2001
agent2 更新：处理人=2002
两人都以为成功，甚至留下两条 CLAIM
~~~

两个请求都在修改前通过了检查。给这段逻辑加事务，仍不能据此认定问题解决。关键是把“还能不能改”的条件放在数据库更新语句里。

~~~sql
UPDATE tickets
SET status = 'IN_PROGRESS', assignee_id = #{actorId}
WHERE id = #{id}
  AND status = 'OPEN'
  AND assignee_id IS NULL;
~~~

这是 TicketMapper.xml 片段。Service 检查返回行数，只有 1 才插入 CLAIM。后到的更新必须重新满足条件，已经变成 IN_PROGRESS 的行不再符合，不能当成功。

最终要验证三项：一个成功结果、数据库里唯一处理人、一条 CLAIM。不能仅比较谁先打印日志。竞争胜者不固定，也不需要固定。

## 3. 完成也使用条件更新

~~~sql
UPDATE tickets
SET status = 'RESOLVED'
WHERE id = #{id}
  AND assignee_id = #{actorId}
  AND status = 'IN_PROGRESS';
~~~

完成与 RESOLVE 事件在同一个事务。事件失败要恢复 IN_PROGRESS；重复完成返回 409，不新增事件。另一处理人无权查看这张单，按不可见规则返回 404。

当前状态机没有重新打开，RESOLVED 和 CANCELLED 是终态。不能把“重复完成返回 409”误认为需要把状态手工改回去。

## 4. 已有脚本怎么操作

确认 A 的服务已加载当前代码，B 切到项目目录，按顺序执行：

~~~powershell
.\scripts\Test-TicketClaim.ps1
.\scripts\Test-TicketResolve.ps1
~~~

每个脚本询问 alice、agent1、agent2 的应用密码，自己管理独立会话、CSRF 与测试工单。不要把 MySQL 密码输入进去。脚本会保留业务记录供 DBeaver 查询，重复执行会产生新编号。

接单脚本预期：IN_PROGRESS、assignee_id=2001、只有一条 actor_id=2001 的 CLAIM。完成脚本预期：RESOLVED、assignee_id=2001，事件按 id 顺序为 CLAIM、RESOLVE，操作者均为 2001。

用户已有工单 56 和 87 的手工成功记录。它们是历史证据，不代表现在必须查询到相同编号；后续清理或换库也可能使历史数据不存在。

## 5. 并发与回滚测试的阅读方法

在 TicketClaimTests 中找两个独立事务竞争的测试，关注线程起点如何尽量同步、每个线程使用哪个身份、最终 SQL 查了什么。不要使用同一条数据库连接模拟两笔独立事务，也不要只顺序调用两遍 claim 冒充并发。

失败方如果在前置查询之后输掉 UPDATE，可返回 409；如果开始查询时别人已经接走而不可见，可返回 404。测试的核心约束是只有一笔成功、最终数据一致，不要求每次调度顺序完全一样。

TicketResolutionTests 验证重复完成、权限和事件失败回滚。Mock 的用途是制造可控故障，真正的事务效果仍需要真实数据库确认。

## 6. 课后练习

1. 写出“取消”和“接单”竞争时，为什么不可能既有成功 CANCEL 又有成功 CLAIM。提示：两个 UPDATE 都要求 OPEN，且各自事件与更新在同一事务。
2. 解释“在 Java 中加 synchronized”为什么不能代替数据库条件更新。参考：锁只能约束同一进程内采用这把锁的代码，多个服务实例或直接数据库操作不共享它。
3. 处理人完成工单后，能否继续在列表里看到？参考：可以，列表包含 assignee_id 等于自己的工单，包含 RESOLVED。
