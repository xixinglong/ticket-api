# 03-05-取消工单与事务回滚详解

本节解决“状态已经改成取消，操作记录却没有写入”的问题。先在 IDE 读代码，再用脚本和数据库验证。事务失败实验应使用测试中的受控故障，不要为了制造失败直接删除正在使用的表。

## 1. 取消成功必须同时发生两件事

第一，tickets.status 从 OPEN 改成 CANCELLED。第二，ticket_events 插入一条 CANCEL，actor_id 为实际创建人。只成功一件会造成业务记录不一致。

事务把两次数据库写入作为一个整体：都成功才提交，任何一步失败则回滚。它不是接口返回值，也不是把 SQL 放在同一个 Java 文件里就自然生效。

## 2. 逐段阅读 TicketService.cancel

~~~java
@Transactional
public void cancel(String id) {
    // 1. 从认证上下文确认 USER 身份。
    // 2. 查工单，并确认创建人等于当前人；否则抛 404。
    // 3. 带 id、创建人、OPEN 条件更新；不是 1 行就抛 409。
    // 4. 插入 CANCEL；不是 1 行就抛运行时异常。
}
~~~

这是流程示意，完整实现以 TicketService.java 为准。Controller 调用 Spring 管理的 Service，事务在业务方法周围建立，返回给 Controller 前完成提交或回滚。

本项目的失败异常都是运行时异常，能够触发默认回滚。不要在方法里 catch 后只打印日志、继续正常返回，这会让调用方以为成功，并可能提交已做的修改。也不要在同一个对象内部普通调用一个加了注解的方法，就认定一定经过事务代理。

## 3. 条件 UPDATE 才是最终判断

~~~sql
UPDATE tickets
SET status = 'CANCELLED'
WHERE id = #{id}
  AND creator_id = #{actorId}
  AND status = 'OPEN';
~~~

这里是 Mapper XML 片段，不是可直接在 DBeaver 运行的 SQL。#{...} 由 MyBatis 绑定参数。

先查询用于判断可见性；查询之后，其他请求可能抢先接单。因此不能仅凭 Java 中看到的 OPEN 就无条件更新。SQL 再检查状态，受影响行数为 1 才能写 CANCEL 事件。

更新 0 行只说明条件不再满足。对于已经确认可见的工单，本项目返回 409；不存在或不可见返回 404。不要让所有失败都返回 200 或统一说“数据库出错”。

## 4. 正常取消怎么验收

按 [[03-04-登录权限与Session练习]] 登录并创建后，使用同一会话与有效 token：

~~~powershell
$cancelResult = Invoke-WebRequest -UseBasicParsing -Method Post -Uri "$base/api/tickets/$($ticket.id)/cancel" -WebSession $aliceSession -Headers $headers
$cancelResult.StatusCode
Invoke-RestMethod -Uri "$base/api/tickets/$($ticket.id)" -WebSession $aliceSession
~~~

预期第一次取消 204，查询状态 CANCELLED。再取消同一张返回 409，不应再插入一条 CANCEL。重复请求在 PowerShell 中会抛 HTTP 异常，属于本次预期失败，不能把异常显示直接当作程序崩溃。

DBeaver 用实际编号查询 tickets 和 ticket_events，核对状态、actor_id=1001、CANCEL 数量=1。已有权限脚本可完成同类检查。

## 5. 回滚测试究竟证明什么

打开 TicketCancellationTests，找到写事件失败及受影响行数异常的用例。先写下三个状态：调用前 OPEN、操作中 UPDATE 已执行、失败后仍 OPEN 且没有 CANCEL。

真实数据库回滚测试需要经过 Spring 管理的事务 Service，并在失败后重新读数据库。只用 Mockito 验证“调用过 mapper”不能证明 MySQL 已回滚；只看抛出异常也不能证明前一条 UPDATE 被撤销。

正常取消、重复取消、别人的工单、已接单工单、事件失败分别测试不同规则，不能用一次成功覆盖全部。

## 6. 课后练习

练习一：把事务去掉会有什么风险？参考答案：状态 UPDATE 可能已提交，而 INSERT 事件失败，留下 CANCELLED 却没有 CANCEL 的数据。不要在现有运行环境实际删注解试错；可在独立练习分支结合回滚测试观察。

练习二：事务能否保证两个处理人不会同时接走同一张单？参考答案：不能只靠 @Transactional；还需要条件更新和行数检查，见 [[03-06-接单并发与完成流程详解]]。

练习三：为什么取消接口不接收 status？参考答案：取消是受规则约束的业务动作，目标状态由服务端决定，客户端不能任意提交 RESOLVED 等状态。
